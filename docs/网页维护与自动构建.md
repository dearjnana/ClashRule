# 网页维护与自动构建

## 日常操作

1. 在 GitHub 打开要修改的规则源，例如 [Gemini](../rules/ai/Gemini.list) 或 [代理补充规则](../rules/network/ProxyLite.list)，点击编辑按钮。
2. 修改域名或正则；每行一个条件，不添加策略组名称。保存时直接提交到 main。
3. 打开 [自动构建规则](https://github.com/dearjnana/ClashRule/actions/workflows/build.yml)，等待对应提交显示绿色成功。
4. 存在生成文件变化时，会出现 `github-actions[bot]` 的“构建：自动同步规则、配置和文件索引”提交。原有 Raw 链接保持有效，无需重新填写地址。

修改规则顺序或指向的策略组，请编辑 [规则顺序](../config/routing.json)；修改策略组成员和筛选条件，请编辑 [策略组配置](../config/groups.yaml)。新建规则文件后，需要在规则顺序中添加引用，才会进入两端主配置。

Gemini 两个组的地区例外：编辑 [官方地区与别名](../config/gemini-regions.json)，由同一数据源生成 OpenClash、Android、Clash Party 的筛选和 [地区对照表](Gemini地区说明.md)。不要在三端分别手改长正则；普通构建不自动抓取 Google 网页，官方范围变化时需要先核对并更新地区源。

## 自动完成的步骤

- 根据 `rules/` 和 `config/` 构建、去重，更新 `generated/rules/`。
- 更新 `providers/`、`profiles/`、`templates/`、Clash Party 中 Gemini 两个组的标记区段、[地区对照表](Gemini地区说明.md)及 [文件索引](仓库文件索引.md)。
- 检查规则格式、优先级回归、策略组引用、仓库链接及中文注释。
- 使用固定版本的官方 SubConverter-Extended 和 Mihomo，验证 OpenClash、Android 与展开配置。测试使用虚拟节点，不访问真实机场。
- 单独验证 Clash Party 覆写的节点列表、节点集合、缺少 MESL、没有可用地区、无缓存下载及关键服务的实际规则命中。缺少 MESL 不影响 Gemini 使用其他机场，没有支持地区时才回退 REJECT。使用真实规则内容与本地测试代理，不接管系统网络。
- 全部通过后，一次提交本次生成结果到 main。没有生成文件变化时，不创建空提交。

每次提交到 main 都会触发，也可在 Actions 页面通过“Run workflow”手动重跑。机器人使用 GitHub 内置令牌，其自动提交不会形成循环构建；无需额外设置个人令牌或上传设备密码。

## 构建失败时

失败不会更新最终生成文件，原有结果继续保留。点开失败任务查看红色步骤，按提示修正规则源并再次提交；日志和验证报告保留七天。已有更新提交时，旧任务跳过发布；工作流不强制推送、不覆盖新提交。

直接手改生成文件会在下一次成功构建时被源文件重新生成。注释或来源说明变化可能不改变有效规则，这种情况下成功但没有新增生成提交是正常的。

## 与订阅转换的关系

这里自动发布的是公开规则、INI 和基础模板，不包含个人机场节点。INI 仍是订阅转换器的外部配置入口，不是可直接导入客户端的节点订阅。

当前两端转换流程仍需 `expand=true`，并由转换流程执行 `tools/finalize.py` 恢复原生策略组。GitHub 构建不会自动登录路由器或替换手机配置。个人订阅的转换、整理及导入方式见 [使用说明](使用与回退.md)；不要将真实订阅地址或转换后的个人配置提交到公开仓库。

## Clash Party 的独立维护方式

[Clash Party 覆写](../clients/clash-party/override.yaml) 直接提供给应用，其中标记区段内的 Gemini 两个组由构建工具更新，其余部分手动维护，提交后 Actions 统一验证。它引用 `rules/` 下的分类源文件，规则内容变化后刷新相应规则集；覆写顺序、策略组、地区筛选或 DNS 变化后，需要刷新远程覆写并重新应用。无需订阅转换器，完整操作见 [专用说明](../clients/clash-party/README.md)。

生成目录的“验证通过后才回写”不等于自动回退源文件：直接提交到 main 的规则源与覆写本身会立即进入仓库。修改前自行检查差异，修改后确认 Actions 成功；失败时修正或撤销相应源文件提交。
